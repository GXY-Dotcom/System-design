# 安德鲁口腔连锁（ADC）诊所管理系统

> 系统分析与设计 · 课程作业
> 姓名：盖心瑶　学号：1602240218

一套面向连锁牙科诊所的完整业务系统，包含**诊所内部管理网页端**与**患者自助微信小程序**，两端共用同一套后端与数据库。系统按真实业务链路设计：从患者来电建档、预约排诊、到诊治疗、逐项计费，到结算单开具与季度业绩核算。

## 三、功能概览

### 管理端（诊所工作台）

| 模块 | 主要能力 |
|---|---|
| 经营概览 | 今日预约数、本月收入、未结金额、近 30 天取消率、收入趋势、今日排诊时间线 |
| 预约管理 | 新建/编辑/删除预约，按诊所联动牙医，登记计划治疗与特殊需求，签到、取消、爽约 |
| 就诊管理 | 就诊记录、追加治疗项目、牙位标注、按单位数与单价自动计价、完成就诊并开单 |
| 结算单 | 一次就诊对应一张结算单，逐行明细（治疗名称/施用单位数/单位价格/小计）、总价、收款、A4 打印 |
| 患者档案 | 建档自动分配账号、多过敏原登记与严重程度、过敏警示、就诊与结算历史 |
| 牙医团队 | 员工编号、资质证书（多对多）、轮转诊所（多对多）、个人业绩 |
| 诊所门店 | 邮政地址、主管姓名、电话、邮箱、办公面积 |
| 治疗项目 | 标准单位价格维护，调价不影响历史单据 |
| 业绩与激励 | 按季度统计收入、耗材成本、运营费用、净利润，激励 = 净利润 × 10%，成本可手工修正后实时重算 |
| 取消率分析 | 趋势折线图、按诊所与患者排名、CSV 导出 |

### 患者端（微信小程序）

查看个人档案与过敏记录、修改联系方式、选择诊所与时段预约、查看/取消自己的预约、查看历史就诊明细、查看并核对结算单。

## 四、业务规则与数据设计

| 规则 | 实现方式 |
|---|---|
| 患者可同时存在多种过敏 | `patient_allergy` 关联表，每位患者多种过敏原，各自带严重程度 |
| 牙医持有多项资质，资质被多位牙医共享 | `dentist_qualification` 多对多 |
| 牙医在多家诊所轮转，患者也可在多家诊所就诊 | `dentist_clinic` 多对多，预约表同时记录诊所与牙医 |
| 一次就诊可涉及多项治疗，就诊中可追加 | `visit_treatment` 一对多 |
| 每项治疗记录施用单位数与单位价格 | `units` × `unit_price` = `subtotal` |
| 跟踪每次预约是否到诊，用于计算取消率 | `appointment.visited` 布尔字段，初始 0，到诊完成后置 1，取消与爽约保持 0 |
| 每次就诊生成一张结算单，单号唯一 | `invoice.visit_id` 上加唯一约束，从数据库层面保证 1:1 |
| 单价调整不影响历史单据 | 单价在下单时**快照固化**到 `visit_treatment` 与 `invoice_line` |
| 季度业绩 | `performance` 表以（牙医, 年, 季度）为唯一键，净利润 = 收入 − 耗材成本 − 运营费用 |

实体关系图见仓库内 `ERD.pdf`。

## 五、技术架构

```
┌──────────────────┐        ┌──────────────────┐
│  管理端网页       │        │  患者端小程序     │
│  原生 HTML/CSS/JS │        │  微信原生 WXML    │
└────────┬─────────┘        └────────┬─────────┘
         │  /api/*                    │  /api/mini/*
         └────────────┬───────────────┘
                      ▼
              ┌───────────────┐
              │  Node.js 服务  │  原生 http 模块，路由表分发
              │  业务规则层    │  计价、开单、状态机、权限校验
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │  SQLite 单文件 │  WAL 模式，外键约束开启
              └───────────────┘
```

- **后端**：Node.js 22 + 内置 `node:sqlite`，零第三方运行时依赖，无需安装任何 npm 包
- **前端**：原生 JavaScript + DOM，无框架、无构建步骤
- **小程序**：微信原生框架，8 个页面，接口地址集中在 `config.js` 一处
- **部署**：PM2 守护 + Nginx 反向代理 + Let's Encrypt 证书
- **数据库**：单文件 SQLite，备份即复制，便于迁移

两端共用同一套业务规则：金额计算、单据生成、状态流转全部在服务端完成，客户端只负责展示，不存在两套逻辑不同步的问题。

## 六、关于域名备案的说明

老师好，关于系统的部署环境，我想单独说明一下域名备案的情况，避免您查看时产生疑问。

**我现在的状况**：系统部署在香港地域的服务器上，域名 `admin.mysmileo.cn` 没有 ICP 备案号。

**为什么这次没能完成备案**：备案必须先有一台**大陆地域**的服务器，由服务商代我向管局提交、初审，再送管局审核，通常要 3 到 7 个工作日；而且审核期间域名必须一直解析到备案的那台机器上，中途不能随意切换。也就是说，要备案就得先买机器、先迁移、再等审核，而这段时间里系统不能中断对外访问。这次作业的交付周期比较紧，这条链路我没能在截止前走完。权衡之后，我选择先用香港的服务器把整套系统和小程序完整跑通、把功能验证到位，保证交付物本身是完整可用的，备案作为独立事项在后面推进。

**对小程序的影响**：小程序我以**体验版**的形式交付。体验版不经过微信的正式发布审核，微信对 request 合法域名的校验只要求域名配置在公众平台后台的白名单里，这一点我已经配置好了，所以体验版能正常请求后端。但如果要正式发布（提交审核上线），微信要求域名具备备案号，未备案会被驳回——这个限制我清楚，是当前的已知缺陷，体验版二维码有效期到 12 月 4 日，我在 README 里标注了。

**我接下来的打算**：提交作业后我就启动这条流程——买一台大陆地域的服务器，把系统整体迁过去（数据库是单文件，复制即可），提交 ICP 备案，审核通过后切换域名解析并重新部署证书；等备案号下来，我再把小程序提交正式审核，让它从体验版转为可以公开访问的正式版本。因为小程序只认域名、不关心服务器在哪，接口地址我也只写在 `config.js` 一个常量里，所以只要域名保持不变，迁移完成后前后端代码都不用改。

以上就是备案这块的完整情况。如果您认为需要补充材料或者调整部署方式，我再改。
